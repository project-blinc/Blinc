# Component catalog

The catalog index links to one page per component at
`/components/cn/<slug>/`. Each detail page has its own description,
Preview | Live | Code tabs, props, keyboard guidance, CSS hooks and canonical
book documentation. The index never starts a demo runtime.

The first six pages cover Button, Input, Select, Dialog, Progress and Charts.
Blocks stay marked as planned until their implementation is available.

## Shared source

- `catalog.json`: route, category, version, documentation section, fixture entry,
  props and restyling metadata.
- `examples/blinc_component_demos/src/demos.rs`: the compiled fixture source.
  A page builds only its selected component inside one dedicated worker.
- `examples/blinc_component_demos/demo.css`: fixture layout.
- `tests/fixtures/violet.css` in the demo crate: hover regression fixture only.
- `detail.js`: built-in theme controls and the side CSS editor.
- `templates/`: static page templates consumed by the existing web build tool.
- `runtime/`: the DOM host, versioned protocol and worker driver.

Native captures and WASM use the same explicit default Hybrid theme, CN styles,
Noto Sans font bytes and fixtures. Dark mode is the default. They do not select a platform theme.
The supplied rounded cursor SVG is coloured violet, outlined in white, and
painted above the captured UI with a cyan halo and click pulse. It is a recording
annotation and never participates in component hit testing.

## Build and preview

From the workspace root:

```sh
CARGO_BUILD_JOBS=2 cargo run -p blinc-build-web-examples -- \
  --catalog-to target/component-site --build
python3 -m http.server 8094 --bind 127.0.0.1 --directory target/component-site
```

Open `http://127.0.0.1:8094/components/`. Use the existing Pages build to stage
alongside the landing page and mdBook. The catalog command replaces only its
`components/` output subtree; use a build directory, never source directories.
The existing example gallery is not regenerated by this command.

`--build` compiles one shared worker bundle and reuses it while its source
fingerprint matches. Site modules and WASM live together under a versioned
release directory. `build-manifest.json` records the source base revision,
dirty state, Cargo.lock hash, features, routes, recording metadata and artifact
SHA-256 checksums. The page labels the published component API separately from
the unreleased worker host.

## Record GIFs

```sh
CARGO_BUILD_JOBS=2 cargo run -p blinc-build-web-examples -- \
  --catalog-to target/component-site --record
```

Add `--only button` to regenerate one component after a component-local change.
Shared theme, font, cursor or choreography changes require refreshing all affected
recordings. A stale recording fails staging instead of publishing a mismatched
preview. Recording requires an offscreen GPU; normal site builds reuse the
checked-in previews and need no native GPU.

The recorder uses a **560 × 320 logical viewport at 2× density**. Interactive
examples stream 48 frames at 60ms per frame into an 1120 × 640 GIF, with a PNG
poster. Noninteractive examples export a PNG only. Full source
frames remain under `target/component-captures/<slug>/frames/`. It retains one
RGBA frame at a time rather than buffering an animation. Scripts move the pointer,
pause over the real control, press/release it and check the resulting state.

Reduced motion uses the poster by default. Preview can be paused explicitly.
Inactive/hidden panels show the poster rather than an animating GIF. Visible grid
cards autoplay their recordings, with pause and reduced-motion support.

## Worker lifecycle

Page entry starts the selected worker in the background. The host transfers a
fresh OffscreenCanvas once, forwards ordered input and owns focus, IME/clipboard,
resize and DPR services. The worker owns Rust state, layout and GPU rendering.
Ready follows the completed first GPU frame. It never changes the selected tab.
Preview, Code and hidden documents pause frame scheduling after warmup; Live
resumes it. Reset and retry dispose the old worker and create a fresh canvas. CSS Apply
replaces one named stylesheet inside the current WASM runtime; deleted rules do
not accumulate and component values remain intact. Escape returns keyboard
focus from the demo to its page controls.

A failed worker keeps the recording, docs and source usable. There is no silent
main-thread fallback. The backend that created the surface is retained in diagnostic metadata. Visitor
status text describes loading and interaction, without renderer implementation details.

## Scoped checks

```sh
CARGO_BUILD_JOBS=2 cargo check -p blinc_component_demos -p blinc_web_hello \
  --target wasm32-unknown-unknown
CARGO_BUILD_JOBS=2 cargo test -p blinc-build-web-examples catalog::pages::tests
CARGO_BUILD_JOBS=2 cargo nextest run -p blinc_component_demos --features capture \
  --test recording --test-threads 1
node --experimental-vm-modules --test web/components/tests/*.test.mjs
node web/components/tests/artifacts.mjs target/component-site
python3 web/components/tests/browser.py --dpr 2
python3 web/components/tests/charts_browser.py
```

The native tests cover real layout, pointer callbacks, pixel density and annotation
ordering. The Node tests cover worker lifecycle/order/failure contracts. The Python
browser checks need Playwright, Pillow and installed Chrome; use your Python
interpreter if its path differs. They launch isolated headless profiles and exercise
actual worker rendering, text input, themes, CSS, chart hosts and pause/disposal.
OS IME and clipboard still need separate browser checks. Compilation and protocol
tests alone do not establish browser GPU support.

## Restyling in Live

The theme control selects actual Hybrid, Restrained or Expressive bundles, so all
colours, focus rings, corners and motion tokens change together. Dark/light is a
separate scheme control. The side CSS editor accepts Blinc CSS targeting the
documented component classes. Apply CSS (Cmd/Ctrl+Enter) refreshes the current UI
without replacing its worker or canvas; Reset CSS removes the named overrides.
Invalid edits leave the current styles intact. Theme changes keep the applied CSS.
Draft typing leaves the current runtime alone. Parse errors stay beside the editor.
The live viewport follows its container automatically.

Installation lives at `/components/installation/` and never redirects to mdBook.
Component and installation source blocks use the bundled highlight.js module.

The catalog header switches the page colour scheme and remembers it across pages;
the live demo follows that scheme. The logo retains its original colours. The CSS
editor and source panels share the landing page syntax palette with line numbers.
Apply and Reset live in the editor toolbar; the focus treatment stays inside it.

Built-in theme-family changes update the existing runtime and reparse its styles
against the new tokens. They keep the worker, canvas, input values and component
state; selecting a theme during warmup applies that choice once the demo is ready.

## Charts family

`/components/cn/charts/` contains separate sections for line, area, stacked area,
grouped bars, stacked bars, horizontal bars, pie, donut, sparkline, threshold,
histogram and comparison charts. Each has its own Preview, Live and compiled Code.
Chart sections load their live host on demand; switching sections releases the
previous additional host. Inactive tabs and offscreen hosts pause their frames.
Only the primary warmed demo and one additional chart host can exist together.
The header colour scheme reaches an embedded chart without reloading it.
The old line-chart URL redirects to the Charts page.

Cursor movement follows the interaction. Button and Input have one approach,
a stationary click or typing pause, and one departure. Extra travel is reserved
for selecting an option, confirming a dialog or exploring chart values.
Noninteractive examples use a still preview without a cursor or playback control;
Sparkline is the first static example.

The editor starts with a component-specific recipe for colours, spacing, shape,
shadows, interactive states and motion. Recipes use the active theme’s root
variables, including `--primary`, `--surface-elevated`, `--radius-lg`,
`--shadow-md`, `--duration-fast` and `--ease-state`. Chart recipes show palette
and grid variables as well as tooltip styling. Later `:root` declarations apply
to earlier component rules; removing an override restores the selected theme.
